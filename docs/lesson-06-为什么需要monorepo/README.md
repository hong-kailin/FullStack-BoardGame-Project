# 第 6 课：为什么需要 monorepo？

## 本节课目标

通过一个具体例子，理解"多仓库"的痛点，从而明白 monorepo 解决了什么问题。

> 本节课是纯概念课，不需要写代码。

---

## 1. 先想象一个场景

假设我们在做一个"璀璨宝石对决"游戏，项目分为三个部分：

| 部分 | 做什么 | 简称 |
|------|--------|------|
| 游戏逻辑 | 卡牌定义、发牌、计分、胜负判定 | `core` |
| Web 界面 | 在浏览器中显示游戏界面 | `web` |
| AI 对手 | 电脑自动出牌 | `ai` |

这三个部分的关系是：

```
web ──依赖──→ core
ai  ──依赖──→ core
```

`web` 和 `ai` 都需要用到 `core` 里的游戏规则代码。比如 `core` 里定义了"一张卡牌长什么样"，`web` 要知道这个定义才能显示卡牌，`ai` 要知道这个定义才能做决策。

---

## 2. 方案一：多仓库（Multi-repo）

传统做法是建三个独立的 git 仓库：

```
splendor-core/    # 单独的 git 仓库
splendor-web/     # 单独的 git 仓库
splendor-ai/      # 单独的 git 仓库
```

### 2.1 怎么让 web 引用 core？

`web` 要使用 `core` 的代码，需要：

1. 把 `core` 的代码**发布到 npm**（`npm publish`）
2. 在 `web` 的 `package.json` 里添加依赖：`"@splendor/core": "1.0.0"`
3. `npm install` 从 npm 官网下载 `core`

### 2.2 问题来了：改一行代码要几步？

假设你发现 `core` 里卡牌分数的计算有个 bug：

```
步骤 1: 去 splendor-core 仓库修改代码
步骤 2: 发布新版本到 npm（npm publish）
步骤 3: 去 splendor-web 仓库更新依赖版本
步骤 4: 去 splendor-ai 仓库更新依赖版本
```

**改一行代码，要走 4 步。**

### 2.3 更多问题

| 问题 | 具体表现 |
|------|---------|
| **发布繁琐** | 每次改 core 都要 `npm publish`，版本号要手动更新 |
| **版本不同步** | web 可能还在用 core@1.0，ai 已经升到 core@1.2，行为不一致 |
| **跨仓库改代码麻烦** | 修一个 bug 可能同时要改 core 和 web，要提两个 PR、两个仓库 review |
| **新人 onboarding 慢** | 要拉 3 个仓库、分别装依赖、分别配环境 |
| **统一配置难** | TypeScript 配置、lint 规则、测试框架，每个仓库各自配一遍 |

> **类比**：多仓库就像你租了三套独立的房子。厨房在房子 A（core），餐厅在房子 B（web），客厅在房子 C（ai）。你在厨房做了菜，得先打包（publish），再端到餐厅（install），菜都凉了。更麻烦的是，想改个菜谱得三套房子来回跑。

---

## 3. 方案二：Monorepo

Monorepo 就是**把所有相关包放在一个仓库里**：

```
FullStack-BoardGame-Project/
├── packages/
│   ├── core/          # 游戏逻辑
│   ├── web/           # Web 界面
│   └── ai/            # AI 对手
└── package.json       # 根配置文件
```

### 3.1 现在改一行代码要几步？

同样修 core 里的 bug：

```
步骤 1: 在项目里修改 core 的代码
步骤 2: web 和 ai 立即就能用上新代码
```

**改一行代码，只需要 1 步。** 不需要发布、不需要更新依赖版本、不需要多个仓库。

### 3.2 Monorepo 解决了什么

| 痛点 | Monorepo 怎么解决 |
|------|-----------------|
| 发布繁琐 | 不用发布，改完直接用 |
| 版本不同步 | 所有包永远用同一个版本的 core |
| 跨仓库改代码 | 一个 PR 就能改所有相关包 |
| 新人 onboarding | 拉一个仓库，`npm install` 搞定 |
| 统一配置 | 一套 TypeScript/lint 配置管所有包 |

---

## 4. 但 monorepo 也有缺点

没有银弹（silver bullet）——每个方案都有 trade-off：

| 缺点 | 说明 |
|------|------|
| 仓库体积大 | 所有代码在一起，git 仓库会变大 |
| 权限控制难 | 不能只给某人 core 的权限而不给 web |
| 构建变慢 | 包多了以后，构建时间增长（Turborepo 解决这个问题） |

> 对个人项目和中小团队来说，monorepo 的缺点基本可以忽略。对大型公司（Google、Meta）来说，他们用专门的工具来解决这些问题。

---

## 5. 什么时候用 monorepo？

| 场景 | 推荐 |
|------|------|
| 个人项目 | ✅ 非常适合 |
| 小团队（< 10 人） | ✅ 非常适合 |
| 多个包互相依赖 | ✅ 非常适合 |
| 大型组织（> 100 人） | ⚠️ 需要专业工具 |
| 要给外部用独立包 | ⚠️ 需要额外配置发布流程 |

---

## 6. 总结

| 概念 | 一句话 |
|------|--------|
| **多仓库** | 每个包一个仓库，改依赖要发布 + 安装 |
| **Monorepo** | 所有包一个仓库，改完直接用 |
| **核心优势** | 减少发布成本、保证版本一致、方便跨包修改 |
| **核心缺点** | 仓库变大、构建变慢（Turborepo 解决） |

---

## 思考题（附答案）

1. **如果 core 发布了 2.0 版本，做了不兼容的改动。在多仓库方案中，web 还能用吗？**
   - 答：能用，因为 web 的 package.json 里写的是 `"@splendor/core": "^1.0.0"`，它不会自动升级到 2.0。但这也意味着 web 永远用不到 core 的新功能。在 monorepo 中，你可以逐步迁移，改一部分测一部分。

2. **Monorepo 能解决"代码复用"的问题吗？**
   - 答：能。多个包共享的类型定义、工具函数放在 monorepo 里，互相引用不需要发布到 npm。比如 `core` 里定义了 `Card` 类型，`web` 和 `ai` 直接 import 就能用。

3. **Google 和 Meta 都用 monorepo，他们的仓库有多大？**
   - 答：Google 的 monorepo 有数十亿行代码、数十 TB 大小。但他们有自研的工具链来处理版本控制和构建。我们小项目的 monorepo 完全不用担心这些问题。
