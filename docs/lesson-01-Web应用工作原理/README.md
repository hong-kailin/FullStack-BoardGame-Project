# 第 1 课：Web 应用是怎么工作的？

## 本节课目标

理解当你打开一个网站时，背后发生了什么。这是全栈开发最核心的宏观图景。

---

## 1. 先做个实验

打开你的终端，执行：

```bash
curl -v https://example.com
```

你会看到一堆输出。我们来拆解它做了什么：

1. 你的电脑（客户端）向 `example.com` 这台服务器发了一条消息："你好，请把你的首页内容给我"
2. 服务器收到消息，把首页的 HTML 内容发回来
3. `curl` 把收到的内容打印到终端

这个"发请求 → 收响应"的过程，就是 **Web 应用最核心的模型**。

---

## 1.5 小知识：curl 是什么？

`curl` 是一个命令行工具，用来**发 HTTP 请求**。你在浏览器里输入网址 → 浏览器帮你发请求 → 显示渲染好的页面。`curl` 做的是同一件事，只不过它在终端里运行，返回的是**原始数据**（HTML 源码），而不是渲染好的页面。

和你熟悉的 Python 做个对比：

```python
import requests

# Python 版：用 requests 库发 HTTP 请求
response = requests.get('https://example.com')
print(response.text)   # 打印服务器返回的 HTML 源码
```

```bash
# curl 版：用 curl 命令做完全一样的事
curl https://example.com
```

等我们以后写后端 API 时，`curl` 是调试接口最常用的工具——不用开浏览器就能测试接口对不对。

> 类比：浏览器 ≈ 带 GUI 的"汽车"（自动挡，一键到达），curl ≈ 发动机本身（手动挡，让你看清每个零件怎么工作）

## 2. 核心概念：客户端 vs 服务器

| 角色 | 是什么 | 类比 |
|------|--------|------|
| **客户端（Client）** | 发起请求的一方，通常是浏览器 | 去餐厅吃饭的**客人** |
| **服务器（Server）** | 响应请求的一方，一台存着网站数据的电脑 | 餐厅的**厨房** |
| **HTTP** | 客户端和服务器之间的通信协议 | 餐厅的**传菜规则**（用什么盘子、怎么传） |

> **类比展开：去餐厅吃饭**
>
> 1. 你看菜单（浏览器输入 URL）
> 2. 告诉服务员你要点什么菜（浏览器发送 HTTP 请求）
> 3. 服务员去厨房下单（服务器收到请求）
> 4. 厨房做好菜（服务器处理请求）
> 5. 服务员把菜端给你（服务器返回 HTTP 响应）
> 6. 你开始吃（浏览器渲染页面）

---

## 3. 从输入 URL 到页面显示——完整流程

在浏览器地址栏输入 `https://www.example.com` 并回车，发生了这些：

```
步骤 1：【DNS 查询】
浏览器问："example.com 这个域名对应的 IP 地址是什么？"
（就像你打电话前先查通讯录）

步骤 2：【建立连接】
浏览器和服务器建立 TCP 连接（三次握手）
（就像你先拨号，对方接听）

步骤 3：【发送 HTTP 请求】
浏览器发送：GET / HTTP/1.1
Host: example.com
（就像你说："你好，我要一份首页"）

步骤 4：【服务器处理】
服务器收到请求，找到 index.html 文件
（厨房找到对应的菜单来准备）

步骤 5：【返回 HTTP 响应】
服务器返回：
HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
（服务员端着菜过来了）

步骤 6：【浏览器渲染】
浏览器把 HTML 解析成页面显示出来
（你开始吃饭）
```

> **对于你来说**：DNS 查询 ≈ DNS 解析（Python 里的 `socket.gethostbyname`），HTTP 请求 ≈ 调用远程 API 获取数据。

## 4. 前端、后端、全栈分别是什么？

### 前端（Frontend）

用户在浏览器里看到和交互的一切。

- **HTML**：页面的"骨架"——标题、段落、按钮、图片
- **CSS**：页面的"衣服"——颜色、字体、布局、动画
- **JavaScript**：页面的"大脑"——点击按钮后的反应、数据验证、动态更新

> 类比：HTML ≈ 人的骨骼，CSS ≈ 穿的衣服，JS ≈ 大脑和肌肉（控制行为）

### 后端（Backend）

在服务器上运行，用户看不到的代码。

- 处理用户登录、注册
- 从数据库读取/写入数据
- 执行业务逻辑（比如游戏规则）
- 提供 API 接口供前端调用

> 类比：前端 ≈ 餐厅的菜单和装修，后端 ≈ 厨房里的厨师和食材

### 全栈（Full Stack）

前端和后端都能写的人。这就是你正在成为的角色。

## 5. 我们现在在哪？

我们的项目"璀璨宝石对决"是一个全栈 Web 应用：

```
┌─────────────────────────────────────────┐
│             浏览器（前端）               │
│  HTML/CSS/JS → 渲染游戏界面             │
│  点击卡牌 → 发送请求                    │
└─────────────────┬───────────────────────┘
                  │ HTTP 请求/响应
                  ▼
┌─────────────────────────────────────────┐
│             服务器（后端）               │
│  游戏逻辑 → 处理操作                    │
│  数据库 → 存用户数据、游戏记录          │
└─────────────────────────────────────────┘
```

目前我们处于阶段零（预备知识），还没开始写游戏代码。但我们做每一步时，都要清楚它在上面这张图的哪个位置。

## 6. 你只需要记住这 3 句话

1. **Web 就是客户端问、服务器答**——发请求、收响应
2. **前端是用户看到的，后端是用户看不到的**——你在浏览器里操作的是前端，在服务器上处理数据的是后端
3. **全栈就是前端后端都懂**——我们的目标

## 思考题（附答案）

1. **打开浏览器开发者工具（F12），切换到 Network 标签，刷新这个页面，观察发起了哪些请求**
   - 答：你会看到很多请求，不只是 HTML 本身。浏览器加载一个页面时，会先请求 HTML，然后解析 HTML 发现里面引用了 CSS、JS、图片等资源，再逐个去请求它们。所以一个页面背后往往有几十个请求。可以按 "Doc" 过滤只看主文档。

2. **如果服务器返回的不是 HTML 而是 JSON（一种数据格式），浏览器会怎么显示？**
   - 答：浏览器不认识 JSON 该怎么渲染成页面，所以它会把 JSON 原文显示出来（一堆花括号和引号的文本），或者直接提示下载。这其实是好事——前端 JS 代码拿到 JSON 后，自己决定怎么用这些数据来更新页面。这也是现代 Web 开发的常见模式（前后端分离）：后端只返回数据（JSON），前端负责渲染。

3. **`curl` 命令和浏览器有什么区别？本质上是相同的还是不同的？**
   - 答：本质上是相同的——都是发 HTTP 请求、收 HTTP 响应。区别在于：浏览器会自动解析 HTML/CSS/JS 并渲染成可视化页面，还会自动处理 Cookie、缓存、图片等；`curl` 只给你原始数据，什么额外处理都不做。所以 `curl` 适合调试（看服务器实际返回了什么），浏览器适合最终用户使用。
